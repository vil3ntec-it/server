# مرکز فرمان — راهنمای کامل

مرکز فرمان، بخشِ تازهٔ همین پنل است: یک جای واحد برای مدیریتِ همهٔ پروژه‌ها،
سرورها، دامنه‌ها، تونل‌ها، حساب‌ها، بکاپ‌ها و پیکربندی‌ها.

از منوی سمتِ راست، بخشِ **مرکز فرمان** را باز کنید.

> **قانونِ اصلی:** هیچ عددی، وضعیتی یا آدرسی ساختگی نیست. هر «آنلاین» یعنی
> برنامه واقعاً به آن آدرس وصل شده. اگر چیزی سنجیده نشده باشد، می‌نویسد
> «بررسی نشده» — نه «آنلاین».

## ۱. اولین کار: انتخاب محل انبار

**مرکز فرمان → انبار**

مسیری را بدهید که همهٔ پروژه‌ها آنجا بنشینند:

```
D:\Projects            (ویندوز)
/srv/ServerData        (لینوکس)
```

برنامه خودش می‌نویسد و پاک می‌کند تا مطمئن شود دسترسی دارد، بعد ذخیره‌اش می‌کند.
برای هر پروژه یک پوشهٔ مستقل ساخته می‌شود:

```
Projects/
├── ShopApp/
│   ├── app/          کدِ برنامه
│   ├── config/       تنظیمات
│   ├── data/         دادهٔ کاری
│   ├── database/     فایل دیتابیس
│   ├── backups/      بکاپ‌های همین پروژه
│   ├── logs/         لاگ‌های همین پروژه
│   ├── releases/     فایل‌های منتشرشده (APK، EXE، …)
│   ├── uploads/
│   ├── cache/
│   └── project.json  شناسنامه (project_id)
└── PumpStation/
    └── …
```

هیچ فایلی از پروژهٔ الف داخل پوشهٔ پروژهٔ ب نمی‌رود. اگر روزی پوشه‌ای را
جابه‌جا کنید، `project.json` می‌گوید مالِ کدام پروژه بوده.

## ۲. پروژه‌ها

**مرکز فرمان → پروژه‌ها → پروژه جدید**

نه نوع پشتیبانی می‌شود:

| نوع | مثال |
| --- | --- |
| اپ اندروید | برنامهٔ فروشگاه روی موبایل |
| برنامه دسکتاپ | نسخهٔ ویندوزی |
| وب‌سایت | سایت معرفی |
| وب‌اپ | پنل تحتِ وب |
| بک‌اند | سرویسِ پشتِ صحنه |
| REST API | `api.example.com` |
| WebSocket | `socket.example.com` |
| دیتابیس | PostgreSQL |
| سرویس | هر چیز دیگر |

هر پروژه یک **`project_id` ثابت** می‌گیرد (مثل `prj_9f2c1a7b`) که هرگز عوض
نمی‌شود — حتی اگر نام یا سرورش تغییر کند.

صفحهٔ اختصاصیِ هر پروژه شش زبانه دارد: نمای کلی، شبکه، حساب‌ها، انبار،
پیکربندی و انتقال.

دکمهٔ **آزمایش همه** همهٔ Endpointها، پورت‌ها و دیتابیسِ آن پروژه را یک‌جا
می‌سنجد و نتیجهٔ واقعی را نشان می‌دهد.

## ۳. سرورها و Agent

**مرکز فرمان → سرورها**

سرورِ خانگی (همین کامپیوتری که پنل رویش است) خودکار ثبت می‌شود. سرورهای
دیگر را دستی اضافه کنید: VPS، اختصاصی، ابری، هاستینگ.

### Agent

برای دیدنِ CPU/RAM/دیسک/سرویس‌های یک سرورِ دیگر، Agent را رویش اجرا کنید:

1. در صفحهٔ سرور → **Agent** → **ساخت کلید**
2. کلید **فقط همان یک‌بار** نشان داده می‌شود — کپی‌اش کنید.
3. پوشهٔ `homelab-panel/agent/` را روی سرورِ مقصد کپی کنید.
4. فایل `agent.env.example` را به `agent.env` تغییرِ نام بدهید و پرش کنید:

```bash
CC_PANEL_URL=https://panel.example.com
CC_SERVER_ID=srv_1a2b3c4d
CC_AGENT_KEY=<کلیدی که دیدید>
CC_SERVICES=api:3000,websocket:4701,postgres:5432
CC_HEALTH_HTTP=http://127.0.0.1:3000/health
```

5. اجرا:

```bash
./start-agent.sh                  # لینوکس / مک
start-agent.bat                   # ویندوز
```

برای همیشه‌روشن بودن روی لینوکس، `control-center-agent.service` را داخل
`/etc/systemd/system/` بگذارید.

**Agent چه می‌کند و چه نمی‌کند:**

- ✅ هر ۳۰ ثانیه گزارشِ واقعیِ سخت‌افزار، شبکه، سرویس‌ها و سلامت می‌فرستد.
- ✅ هر گزارش با **HMAC-SHA256** امضا می‌شود؛ خودِ کلید هرگز فرستاده نمی‌شود.
- ✅ مهرِ زمانیِ هر گزارش بررسی می‌شود، پس گزارشِ کهنه دوباره پذیرفته نمی‌شود.
- ❌ هیچ درگاهی باز نمی‌کند.
- ❌ **هیچ راهی برای اجرای دستور از راه دور ندارد.** حتی اگر پنل هک شود،
  از این‌جا کاری از دستش برنمی‌آید.

## ۴. شبکه: IP، پورت و Endpoint

### IPها

برای هر پروژه چند IP ثبت می‌شود، هرکدام با نوعِ خودش: محلی، شبکهٔ خانگی،
عمومی، سرور، VPS. IPv4 و IPv6 هر دو (نوعش خودکار تشخیص داده می‌شود).

### پورت‌ها — «هیچ پورتی بدون بررسی»

وقتی پورتی اضافه می‌کنید، اول دکمهٔ **اول بررسی کنید** را می‌زنید. برنامه:

1. می‌گردد ببیند همان پورت روی همان سرور برای پروژهٔ دیگری ثبت شده یا نه،
2. واقعاً به آن پورت وصل می‌شود تا ببیند باز است یا نه.

نتیجه یکی از این‌هاست:

- 🟢 **این پورت آزاد است** → ثبت می‌شود.
- 🟡 **باز است ولی برای هیچ پروژه‌ای ثبت نشده** → خبر می‌دهد.
- 🔴 **برای «فلان پروژه» ثبت شده** → ثبت نمی‌شود، مگر با تأییدِ صریح.

### Endpointها

هر Endpoint از اجزایش ساخته می‌شود و آدرسِ نهایی جلوی چشمتان ساخته می‌شود:

```
پروتکل + میزبان + پورت + مسیر + محیط
──────────────────────────────────────
http  ·  192.168.0.102  ·  3000  ·  /api   ·  development
https ·  api.example.com ·  —    ·  /api   ·  production
ws    ·  192.168.0.102  ·  4701  ·  /      ·  development
wss   ·  socket.example.com · —  ·  /socket · production
```

دکمهٔ آزمایشِ کنارِ هر Endpoint یک اتصالِ واقعی می‌زند:

- برای `http/https` یک درخواستِ واقعی + خواندنِ گواهی TLS
- برای `ws/wss` یک **دست‌دادنِ واقعیِ WebSocket** (نه فقط بازبودنِ پورت)

و نتیجه را دقیق می‌نویسد: `آنلاین` · `آفلاین` · `بی‌پاسخ` · `دسترسی ندارد` ·
`خطای SSL` · `خطای DNS` · `خطای اتصال` — همراه با کدِ وضعیت و زمانِ پاسخ.

## ۵. دامنه، ساب‌دامین و تونل

**مرکز فرمان → مسیر دامنه‌ها**

اول دامنه‌ای که خریده‌اید را ثبت کنید (`example.com`). بعد برای هر سرویس یک
مسیر بسازید — ساب‌دامین خودش به دامنهٔ ریشه وصل می‌شود:

```
example.com
      │
      ├── www.example.com     → وب‌سایت
      ├── api.example.com     → تونل ۱ → سرور خانگی → localhost:3000
      ├── app.example.com     → وب‌اپ
      └── socket.example.com  → تونل ۲ → سرور خانگی → localhost:4701
```

دکمهٔ **بررسی دامنه** واقعاً DNS، گواهی SSL، تاریخ انقضای ثبت (WHOIS) و پاسخِ
HTTP را می‌خواند. اگر HTTPS نداشته باشد می‌نویسد «تنظیم نشده»؛ اگر گواهی
منقضی شده باشد می‌نویسد «منقضی».

### چند تونل

هر تعداد تونل می‌توانید داشته باشید و هر تونل چند مسیر:

```
تونل ۱  → سرور خانگی → API
تونل ۲  → سرور خانگی → وب‌سایت
تونل ۳  → بک‌اندِ دسکتاپ
تونل ۴  → WebSocket
```

اطلاعاتشان با هم قاطی نمی‌شود؛ هر مسیر به تونل و پروژهٔ خودش وصل است.

### چرا آدرس ثابت مهم است

IP خانگی عوض می‌شود، ولی کاربر همیشه با `https://api.example.com` وصل
می‌شود. تونل، این آدرسِ ثابت را به `localhost:3000` روی سرورِ شما می‌رساند.
اگر روزی پروژه به VPS رفت، فقط مسیرِ پشتِ همان دامنه عوض می‌شود — کاربر
چیزی نمی‌فهمد.

## ۶. Cloudflare

**مرکز فرمان → Cloudflare**

یک **API Token** از پنل Cloudflare بسازید
(`My Profile → API Tokens`) و اینجا واردش کنید.

- توکن با **AES-256-GCM** رمزنگاری و در گاوصندوق ذخیره می‌شود.
- **هرگز** در رابط کاربری نشان داده نمی‌شود؛ فقط چهار نویسهٔ آخر.
- بلافاصله سنجیده می‌شود تا بدانید کار می‌کند یا نه.

بعد از آن می‌توانید:

- Zoneها را ببینید
- رکوردهای DNS را بخوانید، بسازید، حذف کنید و Proxy را روشن/خاموش کنید
- حالتِ SSL/TLS را ببینید
- تونل‌های واقعیِ Cloudflare و وضعیت و تعدادِ اتصالشان را ببینید
- با **خواندن از Cloudflare** تونل‌ها و مسیرهایشان را یک‌جا وارد کنید

همه از API رسمیِ خودِ Cloudflare. اگر توکن دسترسیِ لازم را نداشته باشد،
همان پیامِ خودشان نشان داده می‌شود.

## ۷. حساب‌ها

**صفحهٔ پروژه → زبانهٔ حساب‌ها**

سه بخش دارد و همه فقط داخلِ همان پروژه:

- **کاربران** — شناسه، نام، تلفن، ایمیل، نقش، فروشگاه، اشتراک، وضعیت، آخرین ورود
- **فروشگاه‌ها** — با `shop_id` یکتا، مالک، مدیر، نشانی
- **اشتراک‌ها** — طرح، شروع، پایان، وضعیت + دکمه‌های ساخت، تمدید، تعلیق، فعال‌سازی، لغو

کاربرِ پروژهٔ الف هرگز در فهرستِ پروژهٔ ب دیده نمی‌شود. اگر بخواهید کاربری را
به فروشگاهی از پروژهٔ دیگر وصل کنید، برنامه جلویش را می‌گیرد.

> رمزِ عبورِ این کاربران این‌جا ذخیره نمی‌شود و کدِ یک‌بارمصرف هم نگه داشته نمی‌شود.

## ۸. بکاپ و بازگردانی

**صفحهٔ پروژه → زبانهٔ انبار**

هر بکاپ یک فایل ZIP است که فقط مالِ همان پروژه است:

```
manifest.json    شناسنامه: project_id، نسخه، تاریخ، شمارش‌ها
database.json    ردیف‌های دیتابیسِ همان پروژه
files/…          محتوای پوشهٔ پروژه (به‌جز backups و cache)
```

بازگردانی همیشه از این چهار پله رد می‌شود:

```
بررسی سلامت  →  پیش‌نمایش  →  تأیید  →  بازگردانی
```

- **بررسی سلامت**: فایل هست؟ جمعِ کنترلی می‌خواند؟ CRC هر فایل درست است؟
  شناسنامه‌اش مالِ همین پروژه است؟ (بکاپِ پروژهٔ الف روی ب کار نمی‌کند.)
- **پیش‌نمایش**: دقیقاً می‌گوید چند فایل، چه حجمی، کدام پوشه‌ها و چند ردیفِ
  دیتابیس برمی‌گردد و کدام پوشه جایگزین می‌شود.
- **بازگردانی**: **اول یک بکاپِ ایمنی از وضعیتِ فعلی** گرفته می‌شود، بعد
  بازگردانی انجام می‌شود.

پیش از **حذفِ پروژه**، **انتقال** و **بازگردانی** همیشه بکاپ گرفته می‌شود.
حذفِ پروژه هم به‌صورت پیش‌فرض فایل‌های روی دیسک را نگه می‌دارد.

## ۹. انتشارها

**صفحهٔ پروژه → زبانهٔ انبار → انتشار جدید**

برای اندروید، ویندوز، لینوکس، مک، وب و بک‌اند.

فایل باید داخلِ پوشهٔ `releases/` همان پروژه باشد — فایلِ بیرونی پذیرفته
نمی‌شود. جمعِ کنترلیِ SHA-256 گرفته و ذخیره می‌شود؛ دکمهٔ بررسی هر وقت
بخواهید دوباره حسابش می‌کند تا مطمئن شوید فایل سالم است.

هر انتشار: نسخه، Build، کانال، حداقل نسخه، اجباری بودن و توضیح دارد.

## ۱۰. پیکربندی مرکزی برنامه‌ها

**صفحهٔ پروژه → زبانهٔ پیکربندی**

به‌جای آنکه آدرس‌ها داخلِ برنامهٔ اندروید هاردکد شوند، از این‌جا خوانده می‌شوند:

```
API_BASE_URL = https://api.example.com/api
WS_URL       = wss://socket.example.com/socket
ENVIRONMENT  = production
API_VERSION  = 2
```

- **نسخه‌دار**: هر ذخیره یک نسخهٔ تازه می‌سازد.
- **قابلِ بازگشت**: هر نسخهٔ قدیمی را می‌شود دوباره فعال کرد.
- **دارای ردِ پا**: هر تغییر در دفترِ رخدادها می‌ماند.
- **بدونِ رمز**: کلیدهایی که بوی رمز بدهند (`password`، `token`، `secret`…)
  رد می‌شوند و باید در گاوصندوق باشند.

مقادیرِ `API_BASE_URL` و `WS_URL` اگر خودتان ننویسید، از Endpointهای ثبت‌شده
ساخته می‌شوند.

### برنامه چطور می‌خواند

یک بار **توکن برنامه** بسازید (فقط همان یک‌بار دیده می‌شود)، بعد:

```bash
curl -H "Authorization: Bearer cfg_prj_…" \
     https://panel.example.com/api/app-config/prj_9f2c1a7b?platform=android
```

```json
{
  "project_id": "prj_9f2c1a7b",
  "environment": "production",
  "version": 3,
  "config": {
    "API_BASE_URL": "https://api.example.com/api",
    "WS_URL": "wss://socket.example.com/socket",
    "ENVIRONMENT": "production"
  },
  "update": { "version": "1.4.0", "mandatory": false, "min_version": "1.2.0" }
}
```

توکنِ هر پروژه فقط برای همان پروژه کار می‌کند.

## ۱۱. گاوصندوق

**مرکز فرمان → گاوصندوق**

برای توکنِ Cloudflare، کلیدهای API، اعتبارنامهٔ دیتابیس و سرور، توکنِ استقرار
و کلیدِ SSH.

- رمزنگاری با **AES-256-GCM**
- کلیدِ اصلی یک فایلِ ۳۲ بایتیِ تصادفی کنارِ دیتابیس است (`data/vault.key`)
  با دسترسیِ `0600`
- مقدار **هرگز** از API بیرون نمی‌رود؛ در رابط کاربری فقط `••••••••` و
  چهار نویسهٔ آخر دیده می‌شود
- سلامتِ گاوصندوق نشان داده می‌شود: چند راز با کلیدِ فعلی باز می‌شوند

> ⚠️ از فایل `data/vault.key` بکاپ بگیرید. بدونِ آن، رازها باز نمی‌شوند.

## ۱۲. پایش و هشدارها

**مرکز فرمان → پایش**

فهرستِ هدف‌ها دستی ساخته نمی‌شود؛ خودش از روی چیزهایی که ثبت کرده‌اید
بازسازی می‌شود: Endpointها، دامنه‌ها، سرورها، تونل‌ها و دیتابیس‌ها. اگر
چیزی را حذف کنید، هدفش هم می‌رود.

هر هدف در فاصلهٔ خودش سنجیده می‌شود و تاریخچه‌اش نگه داشته می‌شود.

### هشدارها

پس از **دو خطای پشتِ‌هم** ساخته می‌شوند (نه با اولین لغزش):

- سرور آفلاین · API آفلاین · تونل آفلاین · خطای دیتابیس
- گواهی رو به انقضا (۲۱ روز) · دامنهٔ رو به انقضا (۳۰ روز)
- بکاپِ ناموفق · فضای کم · CPU بالا · RAM بالا

هشدارها زنده به پنل می‌رسند و می‌شود «دیدم» یا «برطرف شد» زد.

---

## ۱۳. انتقال پروژه به VPS

**صفحهٔ پروژه → زبانهٔ انتقال به سرور دیگر**

اول **نقشهٔ انتقال** را ببینید: دقیقاً می‌گوید کدام Endpointها عوض می‌شوند و
کدام دامنه‌ها دست‌نخورده می‌مانند. بعد تأیید کنید. مراحل:

1. **بکاپِ کامل** (فایل‌ها + ردیف‌های دیتابیس)
2. **انتقالِ بسته** — اگر SSH بدهید با `scp` واقعاً منتقل می‌شود؛ وگرنه گام
   «دستی» علامت می‌خورد و مسیرِ فایل و دستورِ دقیقش نوشته می‌شود.
   **گامی که انجام نشده، هرگز «موفق» ثبت نمی‌شود.**
3. **تنظیمِ آدرس‌ها** روی سرورِ تازه — فقط آن‌هایی که به IP سرورِ قدیم اشاره
   می‌کردند. Endpointهایی که روی دامنهٔ ثابت‌اند دست نمی‌خورند.
4. **نسخهٔ تازهٔ پیکربندی** تا برنامه‌ها آدرسِ درست را بگیرند.
5. **Health Check واقعی** روی آدرس‌های تازه.

گزارشِ گام‌به‌گام می‌ماند و در صفحه دیده می‌شود.

## ۱۴. به‌روزرسانی از GitHub

**مرکز فرمان → به‌روزرسانی**

از خودِ پنل: دکمهٔ **بررسی به‌روزرسانی** و بعد **دانلود و نصب**.

از خطِ فرمان (وقتی پنل بالا نیست):

```bash
cd homelab-panel
./update.sh              # لینوکس / مک
به‌روزرسانی.bat          # ویندوز (دوبار کلیک)

./update.sh --check      # فقط بگو نسخهٔ تازه هست یا نه
./update.sh --rollback   # برگشت به نسخهٔ قبل
```

مراحلِ نصب:

1. آخرین **Release** خوانده می‌شود؛ اگر مخزن Release نداشته باشد، آخرین
   کامیتِ شاخهٔ اصلی.
2. بسته دانلود و **واقعاً بررسی می‌شود** که یک آرشیوِ سالم و مالِ همین
   برنامه است.
3. **از کلِ نصبِ فعلی بکاپ گرفته می‌شود.**
4. فایل‌ها جایگزین می‌شوند — **به‌جز** `data/`، `.env` و `node_modules`.
5. اگر وابستگی‌ها عوض شده باشند `npm install` اجرا می‌شود.
6. پنل خودش را دوباره بالا می‌آورد.

اگر هر گامی بخورد زمین، نصبِ قبلی دست‌نخورده می‌ماند و دکمهٔ **برگشت به
نسخهٔ قبل** هم هست.

در تنظیمات می‌توانید مخزن، کانال (Release یا شاخه) و — برای مخزنِ خصوصی —
یک GitHub Token بگذارید که آن هم در گاوصندوق رمزنگاری می‌شود.

اگر سرورتان فقط از راهِ پراکسی به اینترنت می‌رسد، متغیرهای `HTTPS_PROXY` و
`NO_PROXY` رعایت می‌شوند.

## ۱۵. امنیت و نقش‌ها

### نقش‌های پنل

**مرکز فرمان → کاربران پنل** (فقط مدیر)

مرکز فرمان به همهٔ زیرساخت دسترسی دارد، پس هر کسی نباید هر کاری بکند:

| نقش | چه می‌تواند |
| --- | --- |
| **فقط تماشا** (viewer) | همهٔ صفحه‌ها را می‌بیند و آزمونِ اتصال می‌زند |
| **اپراتور** (operator) | پروژه، سرور، دامنه و Endpoint می‌سازد و ویرایش می‌کند؛ بکاپ می‌گیرد؛ انتشار و پیکربندی ثبت می‌کند |
| **مدیر کامل** (admin) | گاوصندوق، حذف، بازگردانی، انتقال، Cloudflare، به‌روزرسانی و مدیریتِ خودِ کاربرانِ پنل |

- اولین حسابی که می‌سازید همیشه **مدیر کامل** است.
- **آخرین مدیر** را نمی‌شود حذف کرد، از کار انداخت یا نقشش را پایین آورد.
- حسابی که از کار می‌افتد، همان لحظه نشست‌هایش باطل می‌شود.
- چیزی که نقشِ شما به آن دسترسی ندارد، اصلاً در منو نشان داده نمی‌شود — و
  اگر مستقیم هم صدا زده شود، سرور ۴۰۳ می‌دهد و در دفترِ رخدادها ثبت می‌کند.

### HTTPS روی خودِ پنل

اگر پنل را از راهِ تونل باز می‌کنید، Cloudflare خودش https می‌دهد و کاری لازم
نیست. اگر گواهیِ خودتان را دارید، در `.env`:

```bash
HLP_TLS_CERT=/etc/letsencrypt/live/example.com/fullchain.pem
HLP_TLS_KEY=/etc/letsencrypt/live/example.com/privkey.pem
```

پنل مستقیم روی https بالا می‌آید و هر درخواستِ http خودکار به https فرستاده
می‌شود.

### جدولِ کامل


| موضوع | چه کاری شده |
| --- | --- |
| ورود مدیر | رمزِ هش‌شده با scrypt + JWT + نشست‌های قابلِ ابطال |
| نقش‌ها | سه نقش با اجازه‌های انباشتی؛ نوشتن دستِ‌کم اپراتور، کارهای حساس فقط مدیر |
| HTTPS | اختیاری روی خودِ پنل با گواهیِ شما، یا از راهِ تونل |
| مرزِ پروژه‌ها | هر پرس‌وجو با `project_id` بسته می‌شود؛ شناسهٔ درست از پروژهٔ اشتباه هم ۴۰۴ می‌گیرد |
| رازها | AES-256-GCM، کلید در فایلِ `0600`، هرگز در API یا UI |
| Agent | امضای HMAC + پنجرهٔ زمانی؛ بدونِ اجرای دستور از راه دور |
| توکنِ برنامه | مقایسهٔ زمان‌ثابت، مخصوصِ همان پروژه |
| سقفِ درخواست | روی مسیرهای حساس (ورود، Cloudflare، بکاپ، به‌روزرسانی) |
| ورودی‌ها | همه سنجیده و کوتاه می‌شوند؛ فقط فیلدهای مجاز پذیرفته می‌شوند |
| مسیرِ فایل | هر مسیر باید داخلِ پوشهٔ همان پروژه باشد؛ جلوی `../` گرفته شده |
| بازکردنِ ZIP | جلوی zip-slip گرفته شده و CRC هر فایل بررسی می‌شود |
| لاگ‌ها | رمز، کدِ یک‌بارمصرف، توکن و راز هرگز نوشته نمی‌شوند |
| دفترِ رخدادها | هر تغییرِ مهم: چه کسی، چه کاری، کِی، روی چه چیزی، با چه نتیجه‌ای |

## ۱۶. لاگ هر پروژه

**صفحهٔ پروژه → زبانهٔ لاگ‌ها**

هر پروژه پوشهٔ `logs/` خودش را دارد و لاگِ پروژهٔ الف هرگز داخل پوشهٔ ب نمی‌رود:

```
Projects/ShopApp/logs/
├── backup-2026-08-27.log
├── deployment-2026-08-27.log
├── api-2026-08-27.log
└── error-2026-08-27.log
```

هفت رده داریم: `server`، `api`، `authentication`، `sync`، `backup`،
`deployment`، `error`.

خودبه‌خود نوشته می‌شوند وقتی:

- بکاپ گرفته یا بازگردانی می‌شود
- پیکربندی ذخیره یا نسخه‌ای فعال می‌شود
- انتشاری ثبت می‌شود
- پروژه جابه‌جا می‌شود
- **وضعیتِ یک Endpoint یا تونل عوض می‌شود** (نه هر بررسی — فقط وقتی چیزی
  تغییر کند، تا لاگ پر از تکرار نشود)

در صفحه می‌شود بر اساسِ فایل، سطح (`error`/`warn`/`info`) و متن جستجو کرد.

> **رمز، توکن، کدِ یک‌بارمصرف و راز هرگز نوشته نمی‌شوند.** حتی اگر وسطِ یک
> جمله باشند (`token=abc123`) پیش از نوشتن پوشانده می‌شوند.

فایل‌های قدیمی‌تر از ۳۰ روز پاک می‌شوند و هر فایل تا ۸ مگابایت بزرگ می‌شود.
