# معماریِ زیرساختِ سرورِ خانگی

> این سند **پیش از** پیاده‌سازی نوشته شده و مرجعِ تصمیم‌هاست.
> هر تصمیم با دلیلش آمده است؛ اگر روزی دلیل باطل شد، تصمیم هم باید عوض شود.

نسخهٔ سند: ۱ — هم‌راستا با `homelab-panel/server` نسخهٔ ۱.۲

---

## ۱. هدف

یک **زیرساختِ مرکزی** برای سرورِ خانگی که:

- همهٔ سرویس‌ها را از یک جا مدیریت کند (وضعیت، لاگ، ری‌استارت، بکاپ، سلامت)،
- یک **API استاندارد و نسخه‌دار** بدهد که کلاینت‌ها (موبایل/دسکتاپ/وب) فقط با آن حرف بزنند،
- کلاینت هرگز IP سرور را نداند — فقط `https://api.YOURDOMAIN.com`،
- اگر فردا سرور از خانه به VPS رفت، **هیچ کلاینتی تغییر نکند**.

ضدِ هدف (چیزی که عمداً نمی‌سازیم): برای هر اپلیکیشن یک بک‌اندِ جدا. یک زیرساخت،
چند سرویسِ ثبت‌شده در همان زیرساخت.

---

## ۲. نقطهٔ شروع: چه چیزی از قبل هست

این مخزن از صفر شروع نمی‌شود. `homelab-panel/server` امروز این‌ها را دارد و
**همه حفظ می‌شوند**:

| بخش | فایل | وضعیت |
| --- | --- | --- |
| API پنل (Express) | `src/routes/*` | هست — ولی بدونِ نسخه (`/api/...`) |
| احراز هویت | `src/auth.js` | scrypt + JWT + نشستِ دیتابیسی — خوب است |
| دیتابیس | `src/db.js` | SQLite داخلیِ Node — ولی بدونِ migration |
| معیارهای زنده | `src/metrics/*` | CPU/RAM/Disk/Net واقعی — خوب است |
| سایت‌ها و پروسه‌ها | `src/sites/*` | ثبت، اجرا، توقف، سلامت — خوب است |
| دامنه‌ها | `src/routes/domains.js`, `src/lib/domain-check.js` | DNS/SSL/WHOIS واقعی — خوب است |
| تونل اینترنتی | `src/tunnel.js`, `src/site-tunnels.js` | cloudflared — همین «reverse proxy»ِ امروز است |
| سلامت | `GET /health` | سطحی است؛ فقط می‌گوید پروسه بالاست |

**تصمیم ۰ — روی همین بنا می‌سازیم، از نو نمی‌نویسیم.**
دلیل: این کد در حال اجرا روی یک سرورِ واقعی است و داده دارد. بازنویسیِ کامل،
ریسکِ از دست رفتنِ رفتارهایی است که سال‌ها تنظیم شده‌اند (مثلاً منطقِ
«دامنه‌های قُرق» در `protected-hosts.js` که جلوی از کار افتادنِ سایتِ عمومی را
می‌گیرد). کاری که می‌کنیم: **اضافه کردنِ لایه‌های گم‌شده**، نه تعویضِ موتور.

## ۳. مدلِ دامنه

دامنهٔ اصلی در پیکربندی می‌آید (`HLP_DOMAIN`)، نه در کد. در این سند
`YOURDOMAIN.com` یعنی همان مقدار.

| نام | مصرف | چه کسی به آن وصل می‌شود |
| --- | --- | --- |
| `YOURDOMAIN.com` | سایتِ اصلی | مرورگرِ عمومی |
| `www.YOURDOMAIN.com` | تغییرمسیر ۳۰۸ به ریشه | مرورگرِ عمومی |
| **`api.YOURDOMAIN.com`** | **تنها آدرسی که کلاینت‌ها می‌شناسند** | موبایل، دسکتاپ، وب |
| `admin.YOURDOMAIN.com` | پنلِ مدیریت | فقط مدیر |
| `files.YOURDOMAIN.com` | فایل‌های ایستا/دانلود | کلاینت‌های مجاز |

**تصمیم ۱ — جداییِ `api` از `admin` روی دو نامِ متفاوت.**
دلیل: این دو **سطحِ اعتمادِ متفاوت** دارند. `api` باید از کلِ اینترنت در دسترس
باشد؛ `admin` (فایل‌منیجر، اجرای پروسه، تنظیمات) نباید. جدا بودنِ نام یعنی
می‌شود در لبه (reverse proxy یا Cloudflare Access) برای `admin` قانونِ
سخت‌گیرانه‌تر گذاشت — محدود به IP خانه، یا پشتِ لاگینِ دوم — بدونِ اینکه
`api` را خراب کند. امروز هم کدِ موجود همین ایده را دارد: پورتِ `4701` فقط
داده را سرو می‌کند و پنل به اینترنت درز نمی‌کند. ما همان ایده را از «پورت»
به «نامِ دامنه» ارتقا می‌دهیم.

**تصمیم ۲ — کلاینت‌ها فقط `API_URL` را می‌شناسند، آن هم از پیکربندی.**
دلیل: هر جا IP یا پورت داخلِ کلاینت hard-code شود، مهاجرتِ سرور یعنی انتشارِ
دوبارهٔ همهٔ اپ‌ها. با یک نامِ ثابت، مهاجرت فقط یک تغییرِ DNS است.

## ۴. لایه‌ها

```
                     اینترنت
                        │
                        ▼
        ┌───────────────────────────────┐
        │  لبه (Edge)                    │   TLS، هدرهای امن، محدودیتِ نرخ،
        │  Cloudflare Tunnel  یا  Caddy  │   تغییرمسیرِ www، مسیریابیِ نام‌ها
        └───────────────┬───────────────┘
                        │  HTTP داخلی (بدون TLS، فقط روی لوکال‌هاست/شبکهٔ داکر)
        ┌───────────────▼───────────────┐
        │  Backend مرکزی (Express)       │
        │                               │
        │  /health  /ready              │  ← سلامت، برای لبه و مانیتورینگ
        │  /api/v1/*                    │  ← قراردادِ عمومی با کلاینت‌ها
        │  /socket.io/                  │  ← معیارهای زنده به پنل
        │  ws://  (site-sync)           │  ← پروتکلِ دادهٔ سایت
        └──┬─────────┬─────────┬────────┘
           │         │         │
           ▼         ▼         ▼
     ┌─────────┐ ┌───────┐ ┌──────────┐
     │ SQLite  │ │ فایل  │ │ سرویس‌های│
     │ (WAL)   │ │ سیستم │ │ فرزند    │  ← سایت‌ها، دستیارِ هوشمند
     └─────────┘ └───────┘ └──────────┘
```

**تصمیم ۳ — TLS فقط در لبه، نه در Node.**
دلیل: مدیریتِ گواهی (تمدید، ACME، بارگذاریِ مجدد بدونِ قطعی) کارِ حل‌شده‌ای
است؛ Caddy و Cloudflare هر دو خودکار انجامش می‌دهند. آوردنش داخلِ Node یعنی
نوشتنِ دوبارهٔ همان منطق با کیفیتِ کمتر. در عوض Node باید **بداند** که پشتِ
پراکسی است تا IP واقعیِ کاربر (برای محدودیتِ نرخ و لاگ) را از `X-Forwarded-For`
درست بخواند — و این را فقط وقتی باور کند که به او گفته باشیم (`HLP_TRUST_PROXY`)،
وگرنه هر کسی با جعلِ هدر محدودیتِ نرخ را دور می‌زند.

**تصمیم ۴ — یک پروسهٔ Node، چند مسئولیت؛ نه میکروسرویس.**
دلیل: این یک سرورِ خانگی است. میکروسرویس یعنی چند برابر شدنِ نقاطِ خرابی،
حافظه و پیچیدگیِ استقرار، در ازای مقیاسی که لازم نداریم. در عوض داخلِ همان
پروسه، مرزها **ماژولی** است (`routes/`, `metrics/`, `sites/`, `backup/`)، پس
اگر روزی لازم شد یک ماژول جدا شود، مرزش از قبل کشیده شده است.

## ۵. نسخه‌بندیِ API

**تصمیم ۵ — `/api/v1/*` قراردادِ رسمی؛ `/api/*` تا اطلاعِ ثانوی نامِ مستعارِ آن.**

دلیل: رابط کاربریِ ساخته‌شده در `server/public` (فایلِ باندلِ Vite) امروز
`/api/...` صدا می‌زند. اگر مسیر را جابه‌جا کنیم، پنلِ در حالِ اجرا **بلافاصله
می‌شکند** تا وقتی که UI دوباره build شود. پس:

```
app.use('/api/v1', apiV1)     ← قراردادِ عمومی، مستند، پایدار
app.use('/api',    apiV1)     ← همان روتر، برای UIِ فعلی؛ هدرِ Deprecation می‌دهد
```

هر پاسخ از مسیرِ قدیمی هدرِ `Deprecation: true` و `Link: </api/v1/...>; rel="successor-version"`
می‌گیرد تا مهاجرت قابلِ ردگیری باشد. وقتی UI به v1 مهاجرت کرد، اسمِ مستعار حذف می‌شود.

قراردادِ نسخه‌ها: تغییرِ **شکسته** → `v2`. افزودنِ فیلد یا endpointِ جدید →
همان `v1` (کلاینت‌ها باید فیلدهای ناشناس را نادیده بگیرند).

سطحِ ریشهٔ v1:

```
/api/v1/auth        ورود، خروج، تغییر رمز، نشست‌ها
/api/v1/users       مدیریت کاربران و نقش‌ها            (فقط admin)
/api/v1/system      وضعیتِ سرور، CPU/RAM/Disk/Net، نسخه
/api/v1/services    سرویس‌ها/سایت‌ها: وضعیت، اجرا، توقف، ری‌استارت
/api/v1/domains     دامنه‌ها: DNS، SSL، انقضا، اتصال به سرویس
/api/v1/files       فایل‌منیجر                           (admin/operator)
/api/v1/logs        رویدادها و لاگ‌ها
/api/v1/backups     بکاپ: فهرست، ساخت، بازگردانی        (فقط admin)
/api/v1/settings    پیکربندیِ غیرحساس
/api/v1/health      همان /health، برای کلاینت‌هایی که فقط زیرِ /api می‌بینند
```

## ۶. سلامت: `/health` در برابر `/ready`

دو سؤالِ متفاوت، دو جواب:

| مسیر | سؤال | اگر خراب بود چه می‌شود |
| --- | --- | --- |
| `/health` | «پروسه زنده است؟» | ری‌استارتِ سرویس |
| `/ready`  | «الان می‌تواند ترافیک بگیرد؟» | لبه ترافیک نفرستد، ولی ری‌استارت نکند |

**تصمیم ۶ — `/health` سبک و بدونِ وابستگی؛ `/ready` واقعاً وابستگی‌ها را می‌زند.**
دلیل: اگر `/health` به دیتابیس دست بزند و دیتابیس کند شود، health-check تایم‌اوت
می‌خورد و ناظر پروسهٔ **سالم** را می‌کشد — دقیقاً وقتی که نباید. جدا کردنِ این دو،
همان اشتباهِ کلاسیکِ Kubernetes است که از قبل می‌شناسیمش.

`/ready` این‌ها را بررسی می‌کند: نوشتن/خواندنِ SQLite، دسترسیِ نوشتن به
`dataDir`، و بالا بودنِ زیرسیستم‌های اعلام‌شده. خروجی `200` یا `503` با جزئیاتِ
هر بررسی — بدونِ افشای مسیر یا رمز.

هیچ‌کدام احراز هویت نمی‌خواهند (لبه باید بتواند بخواندشان) و **هیچ اطلاعاتِ
حساسی نمی‌دهند**: نه نسخهٔ دقیقِ وابستگی‌ها، نه مسیرِ فایل‌ها، نه نامِ میزبان.

## ۷. امنیت

مدلِ تهدید برای یک سرورِ خانگی که `api` آن روی اینترنت است:

1. اسکنِ خودکارِ اینترنت و brute-force روی ورود،
2. رسیدنِ کسی از `api` به بخش‌های مدیریتی،
3. درزِ راز از راه لاگ، پاسخِ خطا یا Git،
4. دستگاهِ آلوده داخلِ همان شبکهٔ خانگی.

پاسخ‌ها:

| لایه | کار | چرا |
| --- | --- | --- |
| هدرهای امن | `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `HSTS` (فقط پشتِ TLS) | ارزان و بدونِ ریسک؛ جلوی کلِ خانوادهٔ حملاتِ مرورگری را می‌گیرد |
| CORS | فهرستِ سفیدِ مبدأ | امروز کد **هر مبدأیی را بازتاب می‌دهد** و `credentials: true` هم می‌دهد؛ یعنی هر سایتی در اینترنت می‌تواند با توکنِ قربانی به پنل درخواست بزند. این باید اصلاح شود. |
| محدودیتِ نرخ | سخت‌گیرانه روی `auth`، معمولی روی بقیه | brute-force و اسکن |
| اعتبارسنجیِ ورودی | یک کمکیِ مشترک، در مرزِ روتر | جلوگیری از خطاهای ۵۰۰ و تزریق |
| نقش‌ها | `admin` / `operator` / `viewer` | امروز هر کاربرِ واردشده **همه‌کاره** است |
| رازها | فقط از محیط یا دیتابیس؛ هرگز در Git؛ هرگز در پاسخِ API | `.gitignore` امروز `.env` را دارد ✔ |
| لاگ | رویدادِ ورود، تغییرِ نقش، بکاپ، ری‌استارت | ردگیریِ بعد از حادثه |

**تصمیم ۷ — CORS بر پایهٔ فهرستِ سفید، ولی شبکهٔ خانگی به‌صورت پیش‌فرض مجاز.**
دلیل: اگر فقط دامنه را مجاز کنیم، پنل که با `http://192.168.1.20:4700` باز
می‌شود از کار می‌افتد و کاربر فکر می‌کند به‌روزرسانی خرابش کرده. پس مبدأهای
مجاز = زیر‌دامنه‌های `HLP_DOMAIN` + لوکال‌هاست + محدوده‌های IPِ خصوصی
(`10/8`, `172.16/12`, `192.168/16`) + هر چه در `HLP_CORS_ORIGINS` اضافه شود.
مبدأِ ناشناس دیگر بازتاب نمی‌شود.

**تصمیم ۸ — محدودیتِ نرخ در حافظه، نه Redis.**
دلیل: یک پروسه، یک سرور. Redis یک وابستگیِ عملیاتیِ تازه است در ازای مزیتی که
فقط در حالتِ چند-نمونه‌ای معنا دارد. مرزِ ماژولی طوری است که اگر روزی چند
نمونه شد، فقط پیاده‌سازیِ ذخیره‌ساز عوض شود.

**تصمیم ۹ — رازِ امضای JWT از محیط، با پشتیبانِ دیتابیسی.**
دلیل: امروز راز خودکار ساخته و در دیتابیس نگه داشته می‌شود — که برای نصبِ
یک‌کلیکی عالی است و نباید خراب شود. ولی برای استقرارِ جدی باید بشود
`HLP_SECRET_KEY` را بیرون گذاشت تا با بازسازیِ دیتابیس، همهٔ نشست‌ها نپرند و
راز در بکاپِ دیتابیس نباشد. پس: اگر محیط بود از محیط، وگرنه همان رفتارِ فعلی.

## ۸. دیتابیس

SQLite با `journal_mode = WAL`.

**تصمیم ۱۰ — SQLite می‌ماند؛ Postgres نمی‌آوریم.**
دلیل: بارِ کار یک سرورِ خانگی با چند کاربرِ هم‌زمان است. SQLite در Node ۲۲
**داخلیِ خودِ زبان** است (`node:sqlite`) — بدونِ کامپایل، بدونِ وابستگیِ باینری،
بدونِ سرویسِ جداگانه‌ای که باید بالا بماند و بکاپ شود. آوردنِ Postgres یعنی یک
کانتینرِ دیگر، یک رمزِ دیگر و یک نقطهٔ خرابیِ دیگر، برای مقیاسی که وجود ندارد.
مرزِ مهاجرت: اگر روزی نوشتنِ هم‌زمان گلوگاه شد، لایهٔ `db.js` تنها جایی است که
باید عوض شود.

**تصمیم ۱۱ — migrationِ شماره‌دار و یک‌طرفه.**
امروز اسکیمای دیتابیس یک بلوکِ `CREATE TABLE IF NOT EXISTS` است. این یعنی
**افزودنِ ستون به جدولِ موجود ممکن نیست** — روی نصبِ قدیمی هیچ اتفاقی نمی‌افتد
و کدِ جدید با ستونِ گم‌شده می‌شکند. پس:

```
src/db/migrations/001_initial.js      اسکیمای امروز، دست‌نخورده
src/db/migrations/002_users_roles.js  ستونِ نقش
...
```

هر migration در تراکنش اجرا و شماره‌اش در `schema_migrations` ثبت می‌شود.
**بدونِ down-migration** — دلیل: بازگردانیِ خودکارِ اسکیما روی دادهٔ واقعی
بیشتر از آنکه نجات بدهد خرابی می‌سازد. راهِ برگشتِ ما **بازگردانیِ بکاپ** است
که پیش از هر migration به‌صورت خودکار گرفته می‌شود.

## ۹. بکاپ

**تصمیم ۱۲ — `VACUUM INTO` به‌جای کپیِ فایل.**
دلیل: در حالتِ WAL، کپیِ سادهٔ `panel.db` یک فایلِ **نیمه‌کاره** می‌دهد؛
تراکنش‌هایی که هنوز در `-wal` هستند در آن نیستند. `VACUUM INTO` یک نسخهٔ
سازگار و فشرده می‌سازد، بدونِ قفل کردنِ نویسنده‌ها.

- زمان‌بندیِ روزانه + پیش از هر migration
- نگهداری: N نسخهٔ آخر (پیش‌فرض ۱۴)، بقیه خودکار حذف
- بازگردانی: فقط `admin`، با بکاپِ خودکارِ «قبل از بازگردانی» و لاگِ رویداد
- محل: `dataDir/backups` که در `.gitignore` هست ✔

## ۱۰. پیکربندی

همه از متغیرِ محیطی یا `.env` کنارِ سرور. هیچ رازی در Git.

| متغیر | معنی | پیش‌فرض |
| --- | --- | --- |
| `HLP_DOMAIN` | دامنهٔ اصلی | خالی (حالتِ فقط-شبکهٔ-خانگی) |
| `HLP_API_URL` | آدرسی که به کلاینت‌ها اعلام می‌شود | `https://api.<domain>` |
| `HLP_SECRET_KEY` | رازِ امضای JWT | خودکار در دیتابیس |
| `HLP_TRUST_PROXY` | پشتِ پراکسی هستیم؟ | `0` |
| `HLP_CORS_ORIGINS` | مبدأهای اضافی | خالی |
| `HLP_BACKUP_KEEP` | تعدادِ بکاپِ نگه‌داشتنی | `14` |
| `HLP_DATA_DIR`, `HLP_PORT`, ... | (موجود) | — |

**تصمیم ۱۳ — پیش‌فرض‌ها باید بدونِ هیچ تنظیمی کار کنند.**
دلیل: این برنامه با دوبار کلیک روی `نصب-همه-چیز.bat` نصب می‌شود. اگر نبودِ
`HLP_DOMAIN` باعثِ خطا شود، تجربهٔ نصب می‌شکند. پس نبودِ دامنه = حالتِ
شبکهٔ خانگی، نه خطا.

---

## ۱۱. مسیرِ مهاجرت به VPS

چیزی که مهاجرت را ممکن می‌کند این است که **هیچ‌جا IP نوشته نشده**:

1. سرورِ تازه بالا بیاید (`docker compose up -d` یا همان `start-linux.sh`).
2. `dataDir` منتقل شود (بکاپِ SQLite + پوشهٔ سایت‌ها).
3. رکوردِ DNSِ `api.YOURDOMAIN.com` به سرورِ تازه اشاره کند.
4. تمام. هیچ کلاینتی به‌روزرسانی نمی‌شود.

اگر CDN اضافه شد، بینِ مرحلهٔ ۳ و سرور می‌نشیند و باز هم کلاینت‌ها بی‌خبرند.
اگر چند Backend شد، لبه بینشان پخش می‌کند؛ چون نشست‌ها در دیتابیس‌اند نه در
حافظهٔ پروسه، این کار شدنی است.
