# کتابِ رویه‌ها — وقتی چیزی خراب می‌شود

شش خرابیِ واقعیِ یک سرورِ خانگی. هر کدام چهار بخش دارد:
**نشانه** · **سرور خودش چه می‌کند** · **من چه می‌کنم** · **دستورها**.

قاعدهٔ کلی: پیش از هر کارِ دستی، `vill3n status` را بزنید. نودِ نودِ مواقع
خودش می‌گوید کدام‌یک از این شش تاست.

```bash
sudo vill3n status            # سرویس · پنل · پورتِ عمومی · سرورِ حساب · تونل · دستیار · پشتیبان · وابستگی‌ها
sudo vill3n status --json     # همان، برای اسکریپت
```

مسیرها در این سند نسبت به ریشهٔ نصب‌اند (`/srv/vill3n` مگر `VILL3N_ROOT` را
عوض کرده باشید).

---

## ۱) ⚡ قطعِ برق

**نشانه** — سرور خاموش شده و برگشته. پنل چند ثانیه جواب نمی‌دهد؛ ممکن است
وسطِ یک پشتیبان‌گیری یا یک به‌روزرسانی بوده باشد.

**سرور خودش چه می‌کند**

- سرویسِ `vill3n-panel` با `WantedBy=multi-user.target` و `Restart=always`
  ساخته شده: **بی هیچ دخالتی** سرِ بالا آمدنِ سیستم روشن می‌شود. همین‌طور
  `caddy`، `cloudflared`، `ollama` و `docker`.
- دیتابیس روی WAL است و `busy_timeout=5000` دارد؛ نوشتنِ نیمه‌کاره سرِ باز
  شدن خودش برمی‌گردد (rollback)، پس فایل خراب نمی‌شود.
- اگر بازگردانیِ در انتظار مانده بود، **پیش از** باز شدنِ دیتابیس اعمال
  می‌شود (`applyPendingRestore`).
- نصبی که وسطِ کار قطع شده باشد در `.install-state` تا همان مرحله ثبت است؛
  اجرای دوبارهٔ نصب‌کننده از همان‌جا ادامه می‌دهد، نه از اول.

**من چه می‌کنم**

۱. یک دقیقه صبر؛ بعد `vill3n status`.
۲. سبز شد: کاری نمانده. یک پشتیبانِ دستی بگیرید تا وضعِ پس از برق ثبت شود.
۳. سرخ شد: برو سراغِ رویهٔ ۵ (سرویسِ افتاده) یا ۳ (خرابیِ دیتابیس).
۴. اگر نصب وسطِ کار قطع شده بود، همان دستورِ نصب را دوباره بزنید.

```bash
sudo systemctl is-active vill3n-panel caddy cloudflared
sudo vill3n status
sudo vill3n backup
uptime                                    # واقعاً ری‌استارت شده؟
journalctl --list-boots | tail -3
cat /srv/vill3n/.install-state            # نصب تا کجا رفته بود
```

⚠️ UPS هنوز به پنل وصل نیست؛ «قطعِ برق» را از `uptime` و شمارهٔ boot
می‌فهمید، نه از یک هشدار.

## ۲) 💽 پر شدنِ دیسک

**نشانه** — نوشتن‌ها شکست می‌خورند، پنل کند است، پشتیبان ناموفق می‌شود،
کارتِ دیسک در «مانیتورینگ» قرمز است.

**سرور خودش چه می‌کند**

- پایشِ دیسک: زیر **۵ گیگ یا ۱۰٪** ⇒ هشدارِ «فضا رو به اتمام»؛ زیر
  **۱ گیگ یا ۲٪** ⇒ هشدارِ بحرانی.
- ⛔ **زیرِ مرزِ بحرانی پشتیبان‌گیری اصلاً شروع نمی‌شود** — پشتیبانِ ناقص
  بدتر از نبودنش است و دیتابیسِ زنده هم در خطر می‌افتد.
- چرخشِ پشتیبان‌ها خودش کهنه‌ها را می‌برد: **۷ روزانه · ۴ هفتگی · ۳ ماهانه ·
  ۱۰ دستی**، و صفِ `offsite-queue` هم سقفِ **۱۴** فایل دارد.
- سرورِ ثبت‌شده‌ای که مصرفش از ۹۲٪ بگذرد هشدارِ `storage_low` می‌گیرد.

**من چه می‌کنم**

۱. اول ببینید چه چیزی جا گرفته — معمولاً لاگ، صفِ offsite، یا `node_modules`ِ
   سایت‌ها.
۲. صفِ offsite را خالی کنید: یا واقعاً بفرستیدش بیرون، یا اگر مقصدی ندارید
   بدانید که سقفِ ۱۴ تایی‌اش خودش می‌برد.
۳. چرخش را دستی بزنید و پشتیبان‌های کهنه را ببرید.
۴. وقتی جا باز شد، یک پشتیبان بگیرید و **تستِ بازیابی** را اجرا کنید — چون
   ممکن است آخرین پشتیبان‌ها نیمه‌کاره مانده باشند.

```bash
df -h /srv
sudo du -xh --max-depth=2 /srv/vill3n | sort -h | tail -20
ls -l /srv/vill3n/backups/offsite-queue

# چرخش و صفِ خارج از سرور، همین حالا (از راهِ کلیدِ محلی)
KEY=$(sudo cat /srv/vill3n/data/core/local-admin.key)
curl -fsS -X POST -H "X-Local-Key: $KEY" http://127.0.0.1:4700/api/platform/backup/rotate
curl -fsS -X POST -H "X-Local-Key: $KEY" http://127.0.0.1:4700/api/platform/backup/offsite

# لاگ‌های کهنه
sudo journalctl --vacuum-size=200M
sudo du -xh --max-depth=1 /srv/vill3n/logs
```

## ۳) 🗄️ خرابیِ دیتابیس

**نشانه** — پنل بالا می‌آید ولی صفحه‌ها خطا می‌دهند، یا `SQLITE_CORRUPT` در
لاگ، یا `vill3n status` می‌گوید پنل جواب می‌دهد ولی همه‌چیز خالی است.

**سرور خودش چه می‌کند**

- WAL + `busy_timeout` جلوی خرابیِ ناشی از قفل و قطعِ ناگهانی را می‌گیرد.
- پیش از **هر** به‌روزرسانی و هر مهاجرت، خودش پشتیبان می‌گیرد — هم از فایل‌های
  کد و هم از **داده**.
- تستِ بازیابیِ خودکار هفته‌ای یک بار: تازه‌ترین پشتیبان را واقعاً باز
  می‌کند، `PRAGMA integrity_check` می‌زند و شمارِ ردیفِ هر جدول را با
  manifest می‌سنجد. رد شد ⇒ هشدارِ بحرانی. یعنی خرابی معمولاً **پیش از**
  این‌که لازمتان شود پیدا می‌شود.

**من چه می‌کنم**

۱. اول بسنجید که واقعاً دیتابیس خراب است (نه چیزِ دیگری).
۲. **پیش از هر کاری** یک کپیِ خام از فایلِ فعلی بردارید — حتی خرابش.
۳. اگر خراب بود، برو رویهٔ ۴ (بازیابیِ پشتیبان).
۴. اگر `integrity_check` سالم گفت، مشکل جای دیگری است: لاگِ پنل را بخوانید.

```bash
sudo systemctl stop vill3n-panel
sudo cp -a /srv/vill3n/data/core/panel.db /root/panel.db.خراب-$(date +%F)

sqlite3 /srv/vill3n/data/core/panel.db 'PRAGMA integrity_check;'   # باید ok بدهد
# بی sqlite3:
sudo node -e "const{DatabaseSync}=require('node:sqlite');\
const d=new DatabaseSync('/srv/vill3n/data/core/panel.db',{readOnly:true});\
console.log(d.prepare('PRAGMA integrity_check').get())"

sudo systemctl start vill3n-panel
sudo vill3n logs 200
```

⛔ فایلِ `panel.db` را وقتی سرویس روشن است کپی **نکنید** — `vill3n backup`
با `VACUUM INTO` کپیِ سازگار می‌گیرد، `cp` نه.

## ۴) ♻️ بازیابیِ پشتیبان

**نشانه** — داده‌ای پاک شده، یا دیتابیس خراب است، یا یک به‌روزرسانی چیزی را
به‌هم ریخته.

**سرور خودش چه می‌کند**

- هر پشتیبان یک پوشه با `panel.db` و `backup.json` است (شمارِ ردیفِ هر جدول
  در manifest) به‌علاوهٔ یک **آرشیوِ رمزشده** در `backups/offsite-queue`.
- رمزنگاری: `age` اگر روی سیستم باشد، وگرنه AES-256-GCMِ خودِ Node. کلید در
  `secrets/` با ۶۰۰ و **هیچ‌وقت بازنویسی نمی‌شود** — کلیدِ عوض‌شده یعنی همهٔ
  پشتیبان‌های پیشین باز نمی‌شوند.
- ⛔ **پیش از بازگرداندن، خودش از وضعِ فعلی یک پشتیبان می‌گیرد** — همیشه راهِ
  برگشت هست.

**من چه می‌کنم**

۱. فهرست را ببینید و تازه‌ترین پشتیبانِ **سالم** را بردارید.
۲. روی همان یک **تستِ بازیابی** بزنید؛ سبز نشد سراغِ قبلی بروید.
۳. از پنل (پشتیبان‌ها ⇒ بازگرداندن) یا با API بازگردانید.
۴. سرویس را یک بار خاموش و روشن کنید — بی این، دادهٔ تازه خوانده نمی‌شود.
۵. بعدش `vill3n status` و یک نگاه به خودِ داده.

```bash
KEY=$(sudo cat /srv/vill3n/data/core/local-admin.key)

# فهرست و حالِ رمزنگاری و آخرین تستِ بازیابی
curl -fsS -H "X-Local-Key: $KEY" http://127.0.0.1:4700/api/platform/backup

# تستِ بازیابی روی تازه‌ترین پشتیبان — بی دست زدن به دادهٔ زنده
curl -fsS -X POST -H "X-Local-Key: $KEY" \
  http://127.0.0.1:4700/api/platform/backup/restore-test

# بازگرداندن (پنل پیش از آن خودش یک پشتیبانِ ایمنی می‌گیرد)
curl -fsS -X POST -H "X-Local-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"path":"/srv/vill3n/backups/daily/backup-1405-07-03-0300"}' \
  http://127.0.0.1:4700/api/storage/backups/restore

sudo systemctl restart vill3n-panel
sudo vill3n status
```

**اگر فقط آرشیوِ رمزشده را دارید** (مثلاً از هاردِ بیرونی برگشته): آن را
کنارِ پوشهٔ صف بگذارید و از همان‌جا باز کنید — رمزگشایی و باز کردنش همان
کاری است که تستِ بازیابی می‌کند؛ برچسبِ GCM اگر نخواند، فایل دست‌خورده است
و **هرگز بی‌صدا باز نمی‌شود**.

⚠️ `/admin/backups`ِ سرورِ حساب چیزِ دیگری است (کلِ دیتابیسِ آن سرور) و با
پشتیبانِ این پنل یکی نیست. قاطی‌شان نکنید.

## ۵) 🔌 سرویسِ افتاده

**نشانه** — پنل جواب نمی‌دهد، یا دامنه ۵۰۲ می‌دهد، یا برنامه‌ها می‌گویند
«سرورِ حساب روشن نیست».

**سرور خودش چه می‌کند**

- `Restart=always` با `RestartSec=3`: هر افتادنی خودش برمی‌گردد.
- سرورِ حساب فرزندِ خودِ پنل است و ناظرش با تأخیرِ فزاینده دوباره بالایش
  می‌آورد؛ `/api/diagnostics` می‌گوید کدام حال است.
- پایشِ هدف‌ها بعد از چند خطای پشتِ‌هم هشدار می‌سازد (سرور و دیتابیس:
  بحرانی، بقیه: اخطار) و با برگشتنِ سرویس خودش هشدار را برمی‌دارد.
- خودترمیمی هر روز وابستگی‌ها را می‌سنجد: پوشه و دسترسی را **خودش** درست
  می‌کند، ابزار و سرویس را به نصب‌کننده می‌سپارد و خبر می‌دهد.

**من چه می‌کنم**

۱. `vill3n status` — کدام لایه افتاده: سرویس، پنل، پورتِ عمومی، Caddy، تونل،
   یا سرورِ حساب؟
۲. لاگ را بخوانید؛ خطا معمولاً همان سطرِ اول است.
۳. `sudo vill3n repair` — پوشه، دسترسی، سرویسِ خاموش، و هر ابزارِ حذف‌شده.
۴. نشد: سرویس را دستی ببینید و اگر پورت گرفته شده، رقیبش را پیدا کنید.

```bash
sudo vill3n status
sudo vill3n logs 200
sudo systemctl status vill3n-panel --no-pager
sudo vill3n repair                       # بی sudo فقط پوشه‌ها و دسترسی‌ها

# کدام لایه؟
curl -fsS http://127.0.0.1:4700/health   # خودِ پنل
curl -fsS http://127.0.0.1:4701/health   # پورتِ عمومی (تونل به این می‌رسد)
curl -fsS https://api.<دامنه>/api/health # از بیرون
sudo ss -ltnp | grep -E '4700|4701|:80|:443'
sudo systemctl status caddy cloudflared --no-pager
```

⚠️ «پنل بالاست ولی دامنه ۵۰۲ می‌دهد» یعنی مشکل Caddy یا تونل است، نه پنل.
⚠️ «پنل بالاست ولی برنامه‌ها لاگین نمی‌شوند» یعنی سرورِ حساب — `/api/diagnostics`
ردیفِ `accountServer` را ببینید.

## ۶) 🌡️ دمای بالا

**نشانه** — فن بلند است، کامپیوتر داغ است، کارها کند شده‌اند، یا دستیارِ
هوشمند خودش خاموش شده.

**سرور خودش چه می‌کند**

- نگهبانِ دستیار روی دما تصمیم می‌گیرد: **۷۵ درجه ⇒ مکث**، **۸۵ ⇒ خاموش و
  مدل از رَم بیرون**، و زیرِ **۷۰** خودش برمی‌گردد.
- دستیارِ بی‌کار بعد از ۳۰ دقیقه مدل را از رَم بیرون می‌برد (`keep_alive: 0`).
- Ollama از سرِ نصب سقف دارد: یک مدل در رَم، یک درخواستِ هم‌زمان — همان چیزی
  که سرورِ خانگی را داغ نگه می‌داشت.
- پردازنده یا حافظهٔ بالای ۹۲٪ هشدار می‌سازد.

**من چه می‌کنم**

۱. دما را ببینید و مطمئن شوید که واقعاً سخت‌افزار داغ است (نه یک سنسورِ غلط).
۲. اگر دستیار باعثش است، خاموشش کنید و مدلِ کوچک‌تری برگزینید.
۳. آستانه‌ها از تنظیماتِ پنل عوض می‌شوند (`agent_pause_c` · `agent_stop_c` ·
   `agent_resume_c`) — **پایین‌ترشان کنید، بالاتر نه**.
۴. اگر دما بی دستیار هم بالاست، مشکل فیزیکی است: گرد و خاک، فن، جای دستگاه.

```bash
sensors                                   # lm-sensors را نصب‌کننده گذاشته
cat /sys/class/thermal/thermal_zone*/temp  # میلی‌درجه
sudo smartctl -A /dev/nvme0n1 | grep -i temp

sudo vill3n agent off                     # دستیار را بخوابان
sudo vill3n status                        # ببین چه چیزی مصرف می‌کند
ps aux --sort=-%cpu | head -10
```

⚠️ سقفِ دما را برای «سبز شدنِ هشدار» بالا نبرید. هشدار کارش را دارد می‌کند.

## پیوست — یک برگه برای دمِ دست

```bash
sudo vill3n status                  # همه‌چیز در یک نگاه
sudo vill3n repair                  # هرچه خراب یا حذف شده
sudo vill3n backup                  # پشتیبانِ همین حالا
sudo vill3n update                  # پشتیبان ← کدِ تازه ← ری‌استارت
sudo vill3n logs 200                # لاگِ پنل

/srv/vill3n/.install-state          # نصب تا کجا رفته
/srv/vill3n/.install-report         # چه نصب شد، چه رد شد، چه نشد
/srv/vill3n/logs/core/install/      # لاگِ کاملِ نصب
/srv/vill3n/secrets/core.env        # رازها و رمزِ مدیرِ اولیه (۶۰۰)
/srv/vill3n/backups/                # daily · weekly · monthly · manual · offsite-queue
```

نصب از صفر و شرحِ هر مرحله: `docs/INSTALL-fa.md`.
